# Search Algorithms: A*, Min-Max, and Heuristic Search Scenarios

## 1. 🧱 The Core Concept (Basics Refresh)

Search algorithms explore a discrete or discretized continuous state space $\mathcal{S}$ from an initial state $s_0$ to reach a target state $s_{target}$, or to maximize/minimize a dynamic utility function $U(s)$.

```
                 State Space Search Taxonomy
                             │
         ┌───────────────────┴───────────────────┐
         ▼                                       ▼
  Uninformed Search                       Informed Search
(BFS, DFS, Dijkstra)                   (Heuristic Directed)
  • No state domain knowledge             • Guided by heuristic h(s)
  • Explores uniformly                    │
                                 ┌────────┴────────┐
                                 ▼                 ▼
                          Single-Agent        Adversarial
                           (A*, IDA*)      (Minimax, Expectimax)
```

---

### Key Theoretical Foundations

#### 1. Mathematical Guarantees of A* Search
A* selects the next node $n$ to expand by minimizing evaluation function:

$$f(n) = g(n) + h(n)$$

*   $g(n)$: Exact path cost from $s_0$ to node $n$.
*   $h(n)$: Estimated cost from node $n$ to $s_{target}$.

##### Admissibility
A heuristic $h(n)$ is **admissible** if it never overestimates the true minimum cost $h^*(n)$ to reach the goal:

$$\forall n \in \mathcal{S}, \quad 0 \le h(n) \le h^*(n)$$

*Theorem:* If $h(n)$ is admissible, A* tree search is guaranteed to return an optimal path.

##### Consistency (Monotonicity)
A heuristic $h(n)$ is **consistent** if for every node $n$ and every successor $n'$ generated by action $a$ with step cost $c(n, a, n')$:

$$h(n) \le c(n, a, n') + h(n')$$

```
     n ─── c(n, a, n') ───► n'
      \                    /
       \                  /
        \                /
         ►  h(n) ≤ c + h(n')
```

*Theorem:* If $h(n)$ is consistent:
1. $f(n)$ is non-decreasing along any path.
2. When A* expands a node $n$, the path cost $g(n)$ is **strictly optimal**.
3. **No node needs to be reopened or re-visited once placed in the closed set.**

> **Note:** Every consistent heuristic is admissible, but not every admissible heuristic is consistent.

---

#### 2. Min-Max Search & Zero-Sum Games
Used in deterministic, fully observable, two-player zero-sum environments where $\text{Utility}_{\text{Player 1}} + \text{Utility}_{\text{Player 2}} = 0$.

$$\text{Minimax}(s) = \begin{cases} 
\text{Utility}(s) & \text{if Terminal}(s) \\
\max_{a \in \text{Actions}(s)} \text{Minimax}(\text{Result}(s, a)) & \text{if Player}(s) = \text{MAX} \\
\min_{a \in \text{Actions}(s)} \text{Minimax}(\text{Result}(s, a)) & \text{if Player}(s) = \text{MIN}
\end{cases}$$

##### The Horizon Effect & Deep Evaluation
Because game trees grow exponentially with branching factor $B$ and depth $D$, exact Minimax is intractable for complex games (e.g., Chess $B \approx 35, D \approx 80$). Depth-limited search cuts off search at depth $d$ and evaluates states using a static evaluation function $v(s) \approx \text{Utility}(s)$.

## 2. ⚙️ Under the Hood (Internal Mechanics & Architecture)

### Deep Dive: A* Implementation Mechanics

#### Memory Allocation & Open/Closed Management
In production systems, naive pointer-based nodes in heap allocations trigger severe cache misses and allocator lock contention.

*   **Priority Queue (Open Set):** Binary Min-Heap or 4-ary Heap ($O(\log N)$ push/pop, higher cache locality).
*   **State Map (Closed/Visited Set):** Flat hash map storing `node_id -> {g_score, parent_id, flags}`.
*   **Re-opening Problem:** If $h(n)$ is non-consistent, discovering a cheaper path to a node inside the `Closed Set` requires re-inserting it into the `Open Set`, driving worst-case exponential runtime $O(2^N)$.

```
   State Transitions in A*
   
        [ Unvisited Node ]
               │ (Discovered)
               ▼
        ┌──────────────┐
        │   OPEN SET   │◄─────┐ (Path updated via cheaper g)
        │ (Priority Q) │      │ [Only if non-consistent h]
        └──────┬───────┘      │
               │ (Extracted min f)
               ▼
        ┌──────────────┐      │
        │ CLOSED SET   ├──────┘
        │ (Hash Map)   │
        └──────────────┘
```

```python
import heapq
from typing import Dict, List, Optional, Tuple, TypeVar, Callable

T = TypeVar('T')

class AStarPlanner:
    """
    Production-grade A* implementation using flat indexed structures.
    Assumes a consistent heuristic to guarantee zero closed-set reopenings.
    """
    def __init__(self, neighbor_fn: Callable[[T], List[Tuple[T, float]]], 
                 heuristic_fn: Callable[[T, T], float]):
        self.get_neighbors = neighbor_fn
        self.h = heuristic_fn

    def plan(self, start: T, goal: T) -> Optional[Tuple[List[T], float]]:
        # Open Set Priority Queue stores tuples: (f_score, node)
        open_pq: List[Tuple[float, T]] = []
        heapq.heappush(open_pq, (self.h(start, goal), start))
        
        # Tracking costs and predecessors
        g_score: Dict[T, float] = {start: 0.0}
        parent: Dict[T, T] = {}
        closed_set: set[T] = set()

        while open_pq:
            current_f, current = heapq.heappop(open_pq)

            if current in closed_set:
                continue

            if current == goal:
                # Reconstruct path
                path = []
                curr_node = goal
                while curr_node in parent:
                    path.append(curr_node)
                    curr_node = parent[curr_node]
                path.append(start)
                return path[::-1], g_score[goal]

            closed_set.add(current)

            for neighbor, edge_cost in self.get_neighbors(current):
                if neighbor in closed_set:
                    continue

                tentative_g = g_score[current] + edge_cost

                if tentative_g < g_score.get(neighbor, float('inf')):
                    parent[neighbor] = current
                    g_score[neighbor] = tentative_g
                    f_score = tentative_g + self.h(neighbor, goal)
                    heapq.heappush(open_pq, (f_score, neighbor))

        return None # Path not found
```

### Space-Efficient Alternative: IDA* (Iterative Deepening A*)
*   Replaces the priority queue with Depth-First Search.
*   Uses a dynamic $f\text{-limit}$. Initially set to $f(s_0) = h(s_0)$.
*   Iteratively expands nodes in DFS manner. If a path exceeds current $f\text{-limit}$, prune it and track the minimum exceeded $f$-value as the next iteration limit.
*   **Memory Complexity:** $O(D)$ where $D$ is max depth. **Time Trade-off:** Re-evaluates identical nodes across iterations.

### Deep Dive: Minimax with Alpha-Beta Pruning & Transposition Tables

Alpha-Beta pruning drops subtrees by maintaining two bounds during tree traversal:
*   $\alpha$: The minimum score the MAX player is assured of.
*   $\beta$: The maximum score the MIN player is assured of.

When $\beta \le \alpha$ at any node, the current player can force a outcome better than or equal to what the opponent already allowed upstream; therefore, the remaining child branches are **pruned**.

```
                 MAX (alpha=-inf, beta=+inf)
                /   \
               /     \
    (alpha=3) V1=3    V2 (alpha=3, beta=+inf)
                     /  \
                   MIN   ...
                  /   \
                 4     2   <-- MIN selects 2. 
                               Since 2 <= alpha(3), PRUNE sibling branches!
```

#### Transposition Tables & Zobrist Hashing
Due to transpositions (different move orders reaching identical board positions), naive search recomputes subtrees.
1. **Zobrist Hashing:** XOR-based fast state hashing ($H(S) = \bigoplus \text{Table}[piece][square]$).
2. **Transposition Table (TT) Cache Flags:**
   * `EXACT`: Evaluation is precise.
   * `LOWERBOUND`: Fail-high ($\ge \beta$), move was so good it caused a cutoff.
   * `UPPERBOUND`: Fail-low ($\le \alpha$), no move exceeded $\alpha$.

```python
enum_EXACT, enum_LOWERBOUND, enum_UPPERBOUND = 0, 1, 2

class TranspositionTableEntry:
    __slots__ = ['key', 'depth', 'value', 'flag', 'best_move']
    def __init__(self, key: int, depth: int, value: float, flag: int, best_move: Optional[int]):
        self.key = key
        self.depth = depth
        self.value = value
        self.flag = flag
        self.best_move = best_move

class MinimaxAlphaBetaEngine:
    def __init__(self, eval_fn: Callable[[T], float], get_moves: Callable[[T], List[Tuple[int, T]]]):
        self.evaluate = eval_fn
        self.get_legal_moves = get_moves
        self.tt: Dict[int, TranspositionTableEntry] = {}

    def alpha_beta(self, state: T, hash_key: int, depth: int, 
                   alpha: float, beta: float, maximizing: bool) -> float:
        orig_alpha = alpha

        # 1. Transposition Table Lookup
        tt_entry = self.tt.get(hash_key)
        if tt_entry and tt_entry.key == hash_key and tt_entry.depth >= depth:
            if tt_entry.flag == enum_EXACT:
                return tt_entry.value
            elif tt_entry.flag == enum_LOWERBOUND:
                alpha = max(alpha, tt_entry.value)
            elif tt_entry.flag == enum_UPPERBOUND:
                beta = min(beta, tt_entry.value)
            if alpha >= beta:
                return tt_entry.value

        # 2. Terminal or Depth-Cutoff Node
        moves = self.get_legal_moves(state)
        if depth == 0 or not moves:
            return self.evaluate(state)

        # 3. Move Ordering Optimization (PV-Move from TT first)
        if tt_entry and tt_entry.best_move is not None:
            # Re-order moves to put TT best move at index 0
            moves.sort(key=lambda m: 0 if m[0] == tt_entry.best_move else 1)

        best_move = None
        if maximizing:
            value = -float('inf')
            for move_id, child_state in moves:
                # Update hash_key based on move incremental XOR (Placeholder)
                child_hash = hash_key ^ move_id 
                val = self.alpha_beta(child_state, child_hash, depth - 1, alpha, beta, False)
                if val > value:
                    value = val
                    best_move = move_id
                alpha = max(alpha, value)
                if alpha >= beta:
                    break # Beta cutoff
        else:
            value = float('inf')
            for move_id, child_state in moves:
                child_hash = hash_key ^ move_id
                val = self.alpha_beta(child_state, child_hash, depth - 1, alpha, beta, True)
                if val < value:
                    value = val
                    best_move = move_id
                beta = min(beta, value)
                if alpha >= beta:
                    break # Alpha cutoff

        # 4. Save to Transposition Table
        flag = enum_EXACT
        if value <= orig_alpha:
            flag = enum_UPPERBOUND
        elif value >= beta:
            flag = enum_LOWERBOUND

        self.tt[hash_key] = TranspositionTableEntry(hash_key, depth, value, flag, best_move)
        return value
```

## 3. ⚠️ The Interview Warzone (Scenario-based Questions)

### Scenario 1: Scale Pathfinding for Rideshare Routing
**Interviewer:** "You are designing the navigation backend for Uber/Google Maps. You need to compute driving directions between two points across a continent with tens of millions of road segments. Standard A* runs out of memory or takes seconds. How do you execute this query in under 5 milliseconds?"

#### Probing Sequence & Edge Cases
*   *Interviewer:* "What heuristic would you use for regular A*?"
    *   *Candidate:* Great Circle/Euclidean distance divided by max speed limit (to remain admissible).
*   *Interviewer:* "Why does standard A* fail at scale?"
    *   *Candidate:* In flat 2D maps, A* expands an ellipse proportional to path distance. Over a 1,000-mile route, it puts millions of nodes into memory.
*   *Interviewer:* "How do dynamic road conditions (traffic spikes) fit into precomputed structures?"

#### Trade-off Analysis & Architectural Architecture

```
           Dynamic Multi-Tier Routing Pipeline

   Continent-Wide Road Network (Millions of Nodes)
                          │
                          ▼
             [ Contraction Hierarchies ]
             (Precomputes Shortcut Edges)
                          │
           ┌──────────────┴──────────────┐
           ▼                             ▼
   [ Bidirectional A* ]        [ Dynamic Traffic Layer ]
   (Forward from Source,       (Overlay Graph with Real-Time
    Backward from Target)       Edge Cost Mutators)
           │                             │
           └──────────────┬──────────────┘
                          ▼
            Query Returned in < 2ms
```

#### Senior Staff Level Strategy
1. **Contraction Hierarchies (CH):**
   * Preprocessing phase: Order nodes by importance (degree, shortcut counts). Iteratively "contract" (remove) less important nodes and add direct **shortcut edges** between neighbors if the removed node was on the shortest path.
   * Query phase: Run **Bidirectional Dijkstra/A*** restricted to moving *only to higher-importance nodes*. This restricts search space to a tiny fraction of the original graph (e.g., expanding ~1,000 nodes instead of millions).
2. **Dynamic Overlay Customization (Customizable Contraction Hierarchies - CCH):**
   * Decouple topological metric calculation from dynamic costs.
   * Precompute graph topology once. When live traffic updates edge weights every 30 seconds, update only shortcut metrics via parallel matrix operations across upper levels of the hierarchy, avoiding a complete expensive graph re-indexing.

### Scenario 2: Game Engine Under Strict Latency Budget
**Interviewer:** "You are implementing an AI for a competitive board game with an asymmetric tree structure (e.g., Chess or Connect4). You have a strict limit of 100 milliseconds per turn. How do you design the search process to return the best possible move without running over time or missing critical tactical plays?"

#### Probing Sequence & Edge Cases
*   *Interviewer:* "What if you set a fixed search depth of 8, but the 100ms timer runs out at depth 7?"
    *   *Candidate:* The engine crashes or fails to return a move. Fixed-depth search is unpredictable under time budgets.
*   *Interviewer:* "How do you avoid evaluating unstable positions right at the cutoff depth (e.g., right in the middle of a piece capture trade)?"

#### Solution Strategy Framework

```
                       Iterative Deepening Search Engine Loop

                      Start 100ms Timer
                              │
                              ▼
                        Depth = 1
                              │
       ┌──────────────────────►│
       │                      ▼
       │         [ Alpha-Beta Search w/ TT ]
       │                      │
  Increment                   ▼
    Depth         [ Depth Complete? Check Time ]
       │            /                         \
       │       (Time Left)               (Timeout Alert)
       │          /                             \
       └─────────┴─ Return PV Move               ▼
                    from Prev Depth    ABORT & Return Move!
```

1. **Iterative Deepening Framework:**
   Execute depth-1 search, then depth-2, depth-3, up to depth-$N$.
   * When time expires, immediately abort and output the principal variation move from the last fully completed depth.
   * *Overhead:* Since tree growth is exponential ($B^D$), total time spent on depths $1 \dots D-1$ is dominated by depth $D$ (typically $< 10\%-15\%$ total time).
2. **Move Ordering Optimizations (Maximizing Alpha-Beta Pruning):**
   Alpha-Beta best-case performance depends entirely on testing optimal moves *first*:
   * **Hash Move:** Move supplied by the Transposition Table.
   * **Tactical Moves:** Captures ordered by Most Valuable Victim – Least Valuable Attacker (MVV-LVA).
   * **Killer Move Heuristic:** Moves that caused quiet beta-cutoffs at the same depth level in sibling nodes.
3. **Quiescence Search (Solving the Horizon Effect):**
   * Standing at depth 0 cutoff, if the board state is "non-quiet" (e.g., active captures available), *do not evaluate statically*.
   * Continue a restricted search evaluating *only* tactical moves (captures/promotions) until a quiet board state is achieved, preventing erroneous positional assessments.

### Scenario 3: Real-Time Robotics Pathfinding in Continuous Space
**Interviewer:** "An autonomous warehouse robot needs to navigate through dynamic obstacles. The space is continuous, and the robot has kinematic limits (turning radius, maximum acceleration). Standard grid-based A* produces sharp turns the robot cannot execute. How do you adapt heuristic search?"

#### Probing Sequence & Edge Cases
*   *Interviewer:* "Why can't we run standard grid A* and just smooth the path afterwards?"
    *   *Candidate:* Post-smoothing often cuts corners into newly appearing dynamic obstacles, or creates kinematically impossible paths near tight spaces.
*   *Interviewer:* "How do you manage the infinite continuous state space during search?"

```
               Hybrid A* Kinematic Expansion
               
                    Discrete Grid Cell [x, y]
                  ┌───────────────────────────┐
                  │  (Continuous x, y, θ)     │
                  │         \                 │
                  │          \-- Action w1    │
                  │           \               │
                  │            ► State 2      │
                  └──────────────┼────────────┘
                                 │
                                 ▼
                     Prune: Bin states by
                     discrete (X, Y, Theta)
```

#### Senior Staff Level Solution Strategy: Hybrid A*
1. **Continuous State Tracking with Discrete Search Bins:**
   * Maintain state $s = (x, y, \theta)$ in continuous space.
   * Drive transitions by applying discrete control inputs (motion primitives, e.g., steering angle $\delta \in \{-30^\circ, 0^\circ, +30^\circ\}$ over step time $\Delta t$).
   * For the Closed Set/Duplicate detection, map continuous states into discrete spatial-heading 3D grid bins $(X, Y, \Theta)$. If a newly generated state falls into an occupied bin with a higher $g(n)$, prune it.
2. **Dual-Heuristic System:**
   To guide non-holonomic search effectively, combine two heuristics:

$$h(n) = \max \left( h_{\text{non-holonomic}}(n), h_{\text{obstacles}}(n) \right)$$

   * **$h_{\text{non-holonomic}}(n)$:** Ignores obstacles, calculates minimum exact distance considering turning radius constraints (Reed-Shepp curves).
   * **$h_{\text{obstacles}}(n)$:** Ignores vehicle mechanics, computes 2D Dijkstra distance navigating around obstacles.
